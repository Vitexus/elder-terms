# 接続アイコン、Terminal設定の分割、トレイ接続メニューの追加計画

## 目的と保存時点の状態

接続ごとにアイコンを選び、ターミナルとファイル転送のウインドウを見分けやすくする。
ランチャーの接続一覧にも同じ画像を表示する。
システムトレイには接続メニューを追加し、接続名とホットキーを見ながら起動できるようにする。
あわせて、項目が増えたTerminal設定を二つのタブに分ける。

本書は2026年10月21日までの議論を保存したplan6である。
保存時点ではコード調査と計画の作成だけを行い、機能は実装していない。
先に提示した推奨方針を基本として、簡易アイコンブラウザと各表示環境への送信要件を追加した。
実行可否は、ビルド時のバージョンではなく実行時のランタイム環境で判断する。

| --- | --- |

| GUI | Linux、GTK3。ターミナル描画にはboxrigを使用 |
| 調査環境のGTK | 3.24.41。この番号を機能の有効条件には使わない |

## 合意した範囲

| 対象 | 要件 |
| --- | --- |
| アイコンの指定 | デフォルト、Noto Color Emoji、Material Icons、指定した画像ファイルを扱う |
| プリセットの選択 | ポップアップに画像を格子状に並べる。スクロールして探し、クリックで採用する |
| タイトルバー | ターミナルとファイル転送のタイトルバー左端に表示する |
| ランチャーの接続一覧 | 接続名の左側に表示する。未指定時はelder-termsのデフォルト画像を使う |
| X11 | `gtk_window_set_icon_list()`によるウインドウ用アイコンの設定を試行する |
| Wayland | 実行環境が対応する場合、`xdg-toplevel-icon-v1`でウインドウ用アイコンを送信する |
| Ubuntuのドック | 接続ごとのデスクトップエントリーとアプリ識別子を対応させ、指定画像の表示を目指す |
| ランチャー自身 | ウインドウ、ドック、トレイのアプリ用アイコンは現在のものを維持する |
| Terminal設定 | 推奨案Aに従い、動作と外観の二つのタブへ分割する |
| トレイ | `Connections`サブメニューに画像、接続名、設定済みホットキーを表示し、選択した接続を起動する |
| 対応判定 | 実際の表示バックエンド、利用可能な公開API、接続先のプロトコルを実行時に調べる |

ドックへの反映は、起動直後に固定画像が出てから変更されてもよい。
起動前に画像とデスクトップエントリーを準備できる場合は、最初から指定画像を使う。
一つのドックアイコンへ全接続をまとめる方式から、接続単位でまとめる方式へ変更する。
同じ接続の複数ウインドウには同じ識別子を使う。

## 画像形式と保存方法

### 比較した形式と採用方針

[Noto Emoji][noto]と[Material Icons][material]は、SVGとPNGの画像素材を提供している。
検討した形式と判断を次に残す。

| 形式 | 利点 | 注意点と判断 |
| --- | --- | --- |
| 複数サイズの透過PNG | 現在の画像処理を使いやすい。各表示先で同じ画像を扱える | 画像数とサイズ数に応じて容量が増える。配布形式の基本にする |
| SVGを実行時に描画 | 拡大縮小やMaterial Iconsの配色に向く | SVGの読み込み機能が必要。ウインドウやトレイ向けに画素化する処理も要る |
| フォントから画像を生成 | 多数の図柄をフォントとしてまとめられる | フォント選択、絵文字の合成、カラー描画への依存が増える。今回の基本方式にはしない |

Notoは公式PNGを使う。
Materialは公式SVGからビルド時に生成したPNGを配布する方針とする。
SVGを元画像として管理し、実行時は配布PNGを使えるようにする。
XDGの仕様でもPNGが推奨ビットマップ形式であり、SVGの対応は任意である。[Icon Theme Specification][icon-theme]

小さな一覧からドックまで、表示倍率に合った画像を選べるようにする。
サイズの候補は16、24、32、48、64、128、256ピクセルとする。
全画像に全サイズを用意するかは、カタログの容量と縮小品質を測って段階4で決める。
Materialの単色画像は、明るい背景と暗い背景の両方で識別できる配色にする。

素材の版と配布元を固定し、名称と安定したプリセットIDをカタログに保持する。
配布する素材に必要な著作権表示とライセンスを同梱する。
Notoのフォントと画像ではライセンスの扱いが異なるため、実際に採用する画像を確認する。[Notoのライセンス説明][noto]
実行中にGoogle Fontsなどへ画像を取りに行く構成にはしない。

### 接続設定とファイル指定

設定では画像の種類と参照先を区別する。
プリセットは安定したIDを保存し、画像一覧の位置や表示名を識別に使わない。
ファイル指定では、読み込んだ画像を縦横比を保って収める。
正方形の外側には透明な余白を付け、各表示先で同じ図柄に見えるようにする。

未指定、未知のプリセット、画像の欠落、読み込み失敗ではデフォルト画像を表示する。
読み込みに失敗しても、保存した指定を自動で消さない。
設定画面では失敗理由を確認でき、接続自体は起動できるようにする。

指定画像を元のパスから読む方式と、アプリの管理領域へ取り込む方式を段階3で比較する。
ドックからも参照できる保存先、元画像の移動、接続の複製と削除を考慮して決める。
対応する入力形式もこの段階で確定し、PNGを基本として既存の画像読み込み機能を確認する。
GdkPixbufは形式を自動判定するが、実行環境に必要なローダーがなければ読み込めない。[画像読み込みAPI][pixbuf-load]

## 簡易アイコンブラウザ

Generalタブの接続名付近に、アイコンのプレビューと選択ボタンを置く。
接続名、接続種別、接続ホットキーと同じ範囲に置き、ファイル転送でも使えるようにする。
Generalに大きな一覧を常設せず、選択ボタンからポップアップを開く。

ポップアップではNoto Color EmojiとMaterial Iconsを切り替えられるようにする。
選んだプリセットの画像を格子状に並べ、縦方向にスクロールして探せるようにする。
画像をクリックすると設定の編集中の値へ採用し、プレビューを更新してポップアップを閉じる。
閉じる操作だけを行った場合は、元の指定を保持する。
デフォルトへ戻す操作と、画像ファイルを選ぶ操作も用意する。

参考画像で示されたDiscordの絵文字一覧から採用するのは、画像の格子とスクロール選択である。
検索、利用頻度、履歴、お気に入り、カテゴリ階層、絵文字の投稿機能は今回の範囲に含めない。
Discordの画像素材や画面そのものは配布しない。

クリックによる採用は、既存の設定編集の一部として扱う。
ファイル保存や実行中ウインドウへの適用は、既存のApply、Save、Cancelの契約に従う。
Cancelで編集中の変更を破棄でき、Save後は再起動しても選択が復元されることを確認する。

アイコン数が増えても、ポップアップを開くたびに全画像を大きなサイズで読み込まない。
サムネイルの生成と再利用を調整し、選択操作中もUIの応答を保つ。
格子の各項目には名前を付け、キーボードと支援技術からも選択対象を識別できるようにする。

## ウインドウとドックへの表示

### タイトルバーと接続一覧

ターミナルとファイル転送のGtkHeaderBarへ画像部品を追加する。
タイトルバー左側の配置は[GtkHeaderBarの公開API][header-start]を使う。
ウインドウ用アイコンの登録だけで、タイトルバーの表示を満たしたとは扱わない。
接続名の長さ、表示倍率、compact mode、テーマのウインドウ操作ボタンとの配置を確認する。

ランチャーの接続一覧には画像列を追加する。
画像は接続名の左側に置き、選択状態や既存の並び順を維持する。
複数の接続に異なるアイコンを表示し、未指定の接続にはデフォルト画像を表示する。
保存後の一覧更新と、既存の接続ディレクトリー監視にも追従する。

### 実行時の対応判定

表示方式は、環境変数やビルド設定だけで決めない。
実際に使っているGdkDisplayとウインドウを調べ、X11とWaylandの処理を選ぶ。
XWayland経由で動くウインドウはX11として扱う。

Wayland送信には、GTKが所有する`xdg_toplevel`を取得する手段が必要になる。
`xdg_toplevel`はWaylandでトップレベルウインドウを表すオブジェクトである。
調査環境のGTK3には取得用の公開APIがなく、上流には[公開APIと通知の追加][gtk-xdg-accessor]がある。
この差は調査時点の事実として記録し、GTKの版番号で機能を固定しない。

実行中のGTKから公開関数`gdk_wayland_window_get_xdg_toplevel()`を動的に解決する。
その関数や必要な通知が使えるかを、実行時に調べる。
関数の検索には[GModuleの公開API][module-symbol]などを用いる。
関数が見つかったかだけでなく、呼び出せるポインターが得られたことも確認する。
通知の有無は、対象型を初期化してから[GObjectの公開API][signal-lookup]で調べる。

新しいGTKの関数を必須のリンク参照にせず、古いランタイムでもアプリを起動できる構成にする。
古いヘッダーでビルドした場合も、送信機能そのものをコンパイル対象から外さない。
同じバイナリーが、対応するランタイムでは送信し、非対応のランタイムでは接続を継続することを検証する。
別のGTKを同一プロセスに追加ロードして対応させる方式は使わない。

さらにWaylandのregistryから、接続先が`xdg_toplevel_icon_manager_v1`を公開しているか確認する。
registryは、コンポジターが利用可能なプロトコルを通知する仕組みである。
ウインドウ用オブジェクトの生成前は待機し、生成通知を受けて送信する。
能力不足による非対応と、まだウインドウが生成されていない状態を区別する。
ビルド時のGTK版、実行時の版番号、プロトコル定義ファイルの存在だけを対応判定に使わない。

### X11への送信

X11では`gtk_window_set_icon_list()`を呼び出し、複数サイズの画像を設定する。
初回表示と、設定変更による画像の差し替えを対象にする。
デフォルトへ戻した場合も、以前の接続アイコンが残らないようにする。

このAPIを呼んでも、ウインドウマネージャーが画像を採用するとは限らない。[GTKのアイコンAPI][gtk-icons]
API呼び出しだけでなく、X11ウインドウの`_NET_WM_ICON`に渡った画素を検証する。
Ubuntuのドックに採用されたかは、デスクトップ連携の試験で別に確認する。

### Waylandへの送信

公開APIとコンポジターの両方が対応する場合は、`xdg-toplevel-icon-v1`で画像を送る。
GTK3の既存アイコン設定処理だけには任せない。
調査した[GTK3のWayland実装][gtk-wayland]では、通常のアイコンリスト設定処理が空になっている。

送信には[プロトコル定義][xdg-icon]に従った正方形の共有メモリーバッファーを使う。
コンポジターの推奨サイズと表示倍率を考慮する。
アイコンを割り当てた後は内容を変更できないため、差し替え時は新しいアイコンを作る。
バッファーとその記憶領域は、関連するアイコンが必要とする期間保持する。
このプロトコルでは`wl_buffer.release`を使わないことにも注意する。

設定は次のsurface commitで反映される。
GTKの描画処理と整合する時期に送信し、ウインドウの再生成時にも適用する。
GTKから借用したsurfaceや`xdg_toplevel`は破棄しない。
同じsurfaceに新たなトップレベルの役割を二重に設定しない。
待機には既存のイベント処理を使い、ポーリングや待機専用スレッドを追加しない。

公開APIやプロトコルが存在しない環境では送信を行わず、通常の接続と画像選択を利用できるようにする。
選択内容は保持し、タイトルバー、接続一覧、デスクトップエントリーへの適用を続ける。
非対応時の動作確認だけで、対応環境での送信要件を完了したとは扱わない。

このプロトコルは個々のウインドウの画像を指定する。
アプリ全体の画像を使うドックでの表示までは保証しない。[プロトコルの適用範囲][xdg-icon]

### Ubuntuのドックとデスクトップエントリー

デスクトップエントリーは、アプリの名前、画像、起動方法を記した`.desktop`ファイルである。
GNOME Shellは対応するアプリ情報からドック用の画像を取得する。[GNOME Shellの実装][gnome-app]
ウインドウへの画像送信と並行して、接続ごとのデスクトップエントリーを管理する。

保存済み接続には、名前とは別に安定したIDを割り当てる。
名前変更ではIDを保ち、別接続として複製した場合は新しいIDを使う。
ユーザーのアプリケーション領域に、IDに対応する`.desktop`ファイルを生成する。
`Name`に接続名、`Icon`に画像、`Exec`にその接続を開くコマンドを設定する。
`NoDisplay=true`により、通常のアプリ一覧へ接続を並べない。
`Icon`には画像の絶対パスも指定できる。[Desktop Entry Specification][desktop-entry]
接続名やファイルパスの空白、引用符、`%`はdesktopファイルの規則に従って扱う。
`Exec`の引数展開も確認し、シェル用の引用規則だけで組み立てない。

Waylandでは、ウインドウの`app_id`を対応するファイル名に合わせる。
X11では、プロセスのクラスと`StartupWMClass`を対応させる。
非推奨の`gtk_window_set_wmclass()`は使わず、[GDKの公開API][program-class]などで起動時に設定する。
`gdk_set_program_class()`はプロセス全体に適用される。
現在の接続別の子プロセス起動を確認し、別接続の識別子を同じプロセスで上書きしない。
ランチャーの既存ID、desktopファイル、アプリ用画像は変更しない。

接続の保存時、または子プロセスを起動する前にエントリーと画像を準備する。
設定済み画像が最初の表示から使われる経路を優先する。
Waylandでは起動後の`app_id`変更も仕様上は可能だが、ドックの再認識は実機で確認する。[xdg-shell仕様][xdg-shell]

設定変更時はタイトルバーとウインドウ用アイコンを更新する。
ドックについては、画像キャッシュとエントリーの再読み込みも検証する。
実行中の即時更新と、次回起動時の反映を区別して結果を記録する。
画像の保存先は、別プロセスであるデスクトップ環境からも参照できる必要がある。

未保存接続と、保存済み接続を編集中の状態から起動する場合も対象にする。
編集中の画像で保存済み接続のドック画像を意図せず上書きしない扱いを段階6で決める。
接続削除時のエントリーと画像の回収は、実行中ウインドウやドックへの固定も考慮する。
アプリが生成したファイルを識別し、ユーザーが作成したdesktopファイルを削除しない。

## Terminal設定を二つに分ける

### 比較した分割案

| 案 | 第1タブ | 第2タブ | 判断 |
| --- | --- | --- | --- |
| A　動作と外観 | `Terminal`に通信上の文字処理、寸法、履歴、操作設定 | `Terminal appearance`にフォント、枠、カーソル、背景、色補正 | 設定の目的が明確で分量も分散する。採用する |
| B　入出力と画面 | `Terminal input`に文字コード、キー、音、支援機能 | `Terminal display`に寸法、履歴、フォントと全外観 | 画面関連はまとまるが、第2タブの分量が増える |
| C　背景効果を独立 | `Terminal`に背景と色補正以外の項目 | `Background & Colors`に背景と色補正 | 移動範囲は小さいが、Terminal側に多くの項目が残る |

Generalにはファイル転送とも共通する色の設定がある。
新タブは`Terminal appearance`とし、端末専用であることを明示する。
接続アイコンの設定はGeneralに置く。

### 採用案Aの配置

| タブ | 配置する設定 |
| --- | --- |
| Terminal | Character encoding、Backspace code、Cursor key mode、Enter/Return code |
| Terminal | Columns、Rows、Scrollback lines |
| Terminal | BEL sound、Zoom in shortcut、Zoom out shortcut、Send BREAK shortcut、Screen reader access |
| Terminal appearance | Font families、Font size |
| Terminal appearance | Show window side borders、Window side border width |
| Terminal appearance | Cursor shape、Cursor blinking |
| Terminal appearance | 背景モード、透明度、色付けと強度、画像と不透明度、画像配置 |
| Terminal appearance | 色フィルタ、色覚補正、補正強度、比較プレビュー |

分割では設定の意味と保存キーを維持する。
ランチャー側と実行中ターミナル側の設定画面に同じ分類を適用する。
端末専用のタブをファイル転送の設定画面には表示しない。
既存の設定継承、検証、Apply、Save、Cancel、描画方式表示も維持する。

## システムトレイの接続メニュー

現在の固定メニューに`Connections`サブメニューを加える。
内容はランチャーと同じ保存済み接続一覧とし、並び順も合わせる。
各項目には接続アイコン、Connection name、設定がある場合のホットキーを表示する。

```text
Open elder-terms
Connections >
    [icon] Production SSH (Ctrl+Alt+P)
    [icon] Development SFTP
    [icon] Local shell (Ctrl+Alt+T)
Application settings
About elder-terms
Quit
```

StatusNotifierItemは、D-Busでデスクトップ環境へトレイの情報を渡す方式である。
この経路ではDBusMenuのサブメニュー構造と画像データを使う。
現在の固定レイアウトを更新できるよう、メニューのリビジョンと変更通知も扱う。[DBusMenu仕様][dbusmenu]

確認した[UbuntuのAppIndicator実装][ubuntu-menu]は、`shortcut`属性を表示に使っていない。
そのため、Ubuntuで必要な表記が欠けないよう、接続名のラベルへ`Ctrl+Alt+X`などを含める。
標準のショートカット属性を併用する場合は、他のホストで二重表示にならないことも確認する。
右端への列揃えを必須にせず、アイコン、名前、キー表記が読めることを要件にする。

XEmbed経路のGtkMenuにも同じサブメニューを追加する。
画像にはGtkMenuItemへGtkImageなどを組み合わせ、非推奨のGtkImageMenuItemは使わない。[GTKの移行説明][image-menu-item]
トレイのアプリ用アイコン自体は変更しない。

接続一覧は、ホットキー登録に成功した接続だけから作らない。
キー未設定や登録競合のある接続も一覧に含め、キーの表示は保存した設定から得る。
重複名などに依存せず、対応する接続ファイルを確実に特定して起動する。

選択時は、既存の保存済み接続の起動処理を再利用する。
ターミナルとファイル転送を接続種別に応じて起動する。
ランチャーで編集中の別接続や、その未保存の値を起動対象に混ぜない。
メニュー表示後に接続が削除された場合は、別の接続を誤って起動せず失敗を通知する。

保存、追加、削除、名前変更、アイコン変更、ホットキー変更をメニューへ反映する。
接続がない場合は空であることが分かる非操作項目を表示する。
表示中のメニュー更新、トレイホストの再接続、ランチャーを隠した状態での起動も確認する。

## 実装の段階と完了条件

各段階は、単独でビルドと対象テストを実行できる単位にする。
先に期待する動作のテストを追加してREDを確認し、実装後にGREENを確認する。
新たな問題が見つかった場合は原因と計画の前提を見直す。
各段階の成果と検証をコミットし、実装の結果を本書へ追記する。

### 段階1　実行時の能力判定とネイティブ送信を小さく検証する

X11とWaylandの公開API、APIコメント、プロトコル定義を確認する。
既存のC++テストドライバーに合わせ、固定画像を表示・送信できる最小の実行例を作る。
実際のバックエンド判定、公開関数の動的解決、通知、registry探索を検証する。
対応するGTKの版番号を条件にせず、実行時に利用できる機能から判定する。

同一バイナリーを能力の異なる環境で動かす。
APIなし、プロトコルなし、生成待ち、送信可能の各状態を観測する。
APIなしの環境でもロード時エラーにならず、対応環境では受信側まで画像が届くことを確認する。
テスト用の受信側はプロトコルと画素を検証し、ソース中の関数名の有無を検査する方式にはしない。

完了条件は、各状態での実際の動作と公開APIだけを使う送信経路を確認できることである。
対応環境を用意できない場合は未検証として記録し、送信要件を完了扱いにしない。
コミットは`feat: probe native window icon capabilities at runtime`を想定する。

### 段階2　Terminal設定を分割する

案Aの配置で二つのタブを作り、共有設定画面へ組み込む。
各項目を新しい場所から操作し、値の適用、保存、取り消し、再表示を検証する。
ターミナルとファイル転送で、表示すべきタブが正しいことも確認する。

完了条件は、項目が欠けず重複せず、保存形式と既存の設定操作を維持することである。
この段階だけで、新しい設定画面を実アプリから観測できるようにする。
コミットは`refactor: split terminal behavior and appearance settings`を想定する。

### 段階3　ファイル指定と共通のアイコン表示を追加する

接続アイコンの設定、画像の読み込み、デフォルトへの復帰を追加する。
Generalにプレビューと画像ファイルの選択を設ける。
ターミナルとファイル転送のタイトルバー、ランチャーの接続一覧まで反映する。
画像ファイルの保存方法と対応形式を決め、欠落時も接続できることを検証する。

完了条件は、異なる接続に画像を設定し、保存と再起動で同じ画像を復元できることである。
Apply、Save、Cancel、未指定、読み込み失敗も確認する。
コミットは`feat: add configurable connection icons`を想定する。

### 段階4　プリセットと簡易ブラウザを追加する

配布するNotoとMaterialの版、画像、カタログ、ライセンスを用意する。
Generalから開くポップアップへ二つのプリセットを組み込む。
スクロールで画面外の画像へ移動し、クリックで選択する操作を検証する。
各画像を大きく読み込む方式とサムネイル再利用を比較し、容量と応答性を確認する。

完了条件は、両プリセットを選択でき、後方の画像も選べ、選択結果が各表示先へ反映されることである。
選択を取り消せることと、保存後の復元も確認する。
コミットは`feat: add preset connection icon picker`を想定する。

### 段階5　X11とWaylandへ接続アイコンを送信する

段階1の公開APIによる処理を、実際のターミナルとファイル転送に組み込む。
初回表示、画像変更、デフォルトへの復帰、ウインドウ再生成を扱う。
X11のプロパティとWaylandの受信内容を検証する。
Waylandのバッファー寿命、更新後の画像、終了時の資源解放も確認する。

完了条件は、同じバイナリーで実行時の対応を判定し、対応環境では送信、非対応環境では正常な接続継続を確認できることである。
コミットは`feat: publish connection icons to X11 and Wayland`を想定する。

### 段階6　接続ごとのドック表示を追加する

安定した接続ID、ユーザー領域のdesktopファイル、外部から参照できる画像を管理する。
起動前の準備と、X11・Waylandそれぞれのアプリ識別を組み込む。
名前変更、複製、削除、未保存状態からの起動について扱いを確定する。
実行中ウインドウと生成ファイルの寿命を確認する。
空白や記号を含む接続名とファイルパスでも、選択した接続を起動できることを検証する。

完了条件は、Ubuntuの対応する実環境で、異なる接続を異なるドック画像として識別できることである。
同じ接続のグループ化、最初の表示、実行中の変更、再起動後の復元を記録する。
X11では、接続別のプロセス構造と識別子の対応も完了条件に含める。
desktopファイルの内容検査だけで、ドック表示の検証を代用しない。
コミットは`feat: add per-connection desktop identities`を想定する。

### 段階7　トレイから接続を起動する

二つのトレイ経路にConnectionsサブメニューを追加する。
画像、接続名、ホットキーを表示し、既存の起動処理へ接続する。
設定監視とメニュー更新をつなぎ、ホストの再接続にも追従する。

完了条件は、ホットキーの有無にかかわらず全保存済み接続が表示され、選択した接続を正しく起動できることである。
Ubuntuでキー表記が見えることと、接続の追加・変更・削除の反映を確認する。
コミットは`feat: launch saved connections from the tray`を想定する。

### 段階8　回帰確認と利用者向け説明を仕上げる

各表示先と設定操作を組み合わせ、既存の接続、ホットキー、compact mode、背景設定への回帰を確認する。
画像選択中やメニュー更新中も、通信とUIの操作を継続できることを確認する。
通常ビルドと配布用ビルドを行い、警告は原因を分析して対処する。
ルートの`make test`または同じ全ワークスペースを対象にした全体テストを最後まで実行する。
試験中はコミットを固定し、時間経過だけに頼る待機を避ける。

利用者向け文書は日本語を原本として更新し、英語版へ反映する。
画像形式、選択方法、ドックのグループ化、環境による表示差を説明する。
一般文書から本計画へのリンクは追加しない。

完了条件は、次節の受入条件を満たし、検証結果と制約を記録することである。
変更内容に応じて`fix:`、`chore:`、`doc:`のコミットへ分ける。
