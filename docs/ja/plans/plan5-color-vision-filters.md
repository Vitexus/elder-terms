# 色覚特性に配慮した端末色フィルタの追加計画

## 目的と保存時点の状態

端末の文字や背景に使われる色を、利用者が区別しやすい色へ補正する。
既存のOklch補正と併用し、文字の読みやすさと色分けの識別を両立させる。
対象には、差分表示、ログ、色付き背景で状態を示す端末アプリを含める。

本書は2026年10月20日のコード調査と検討を保存したplan5である。
保存時点では計画の作成だけを行い、機能の実装や効果の検証は行っていない。
再配色方式を優先する方針と、設定・適用範囲・評価条件を記録する。
具体的な変換方式、係数、補正強度の範囲と既定値は、段階1の評価で選定する。

## 現在の補正と追加する機能

Oklchは、明るさ、鮮やかさ、色相を分けて表す色の方式である。
[現在の補正](../../../elder-terms-terminal/src/terminal-color-filter.cpp)は色相を保ち、主に明るさを調整する。
文字やマーカーと背景とのコントラストが4.5:1以上なら、その色を変更しない。
それ以外は明るさを調整し、sRGBで表せる範囲を超える場合に鮮やかさを下げる。
無彩色は無彩色のまま扱う。
既存の要件と検証記録は[plan4](plan4-terminal-appearance.md)にある。

この処理で赤と緑の文字がそれぞれ読みやすくなっても、二色を区別できるとは限らない。
色覚特性に配慮するには、背景との明暗差に加えて、色同士の識別を評価する必要がある。
追加機能では、識別しづらい色の情報を別の色差へ移す再配色を行う。
この種の処理はDaltonizationと呼ばれる。

P型向け、D型向け、T型向けの補正を候補とする。
対応する呼称はprotan、deutan、tritanである。
P型・D型では赤緑系、T型では青黄系の識別を主な評価対象にする。
この分類だけで個々の利用者の見え方を決めつけず、本人が補正の強さを選べる構成とする。

## 方式の比較と採用方針

ANSI16色は端末の基本パレット、256色は番号で指定する拡張パレットである。
TrueColorでは、アプリがRGB値を直接指定する。

| 方式 | 利点 | 留意点 |
| --- | --- | --- |
| 色覚特性に合わせた再配色 | ANSI16色、256色、TrueColorを共通の処理で扱える | 補正によって別の色同士が似る場合がある。強度調整と評価が必要 |
| 識別しやすいANSI16色パレットへの置換 | 基本色を使う差分表示などについて、配色全体を設計できる | TrueColor指定には適用できない。アプリ独自のパレットとの関係も考慮する必要がある |

今回の追加では、対象が広い再配色方式を優先する。
ANSI16色の置換は比較候補として残すが、パレット編集機能の追加までは含めない。
再配色の方式選定では、識別の改善、元の色からの変化、表現可能な色範囲の三点を比較する。
色範囲の端へ値を丸めることで、別々の色が同じ色になる場合にも注意する。
[Farupの研究][daltonization]でも、再配色による情報の回復と、色範囲の制限による情報の欠落が扱われている。

色覚シミュレーションは、色覚特性による見え方を近似する処理である。
補正前後の評価に使い、表示する色を改善する再配色は別に設計する。
模擬モデルには[Brettelらの方式][brettel]などを検討する。
P型・D型・T型ごとの条件を評価し、型を変更しても同じ係数を流用するだけの実装にはしない。
文献を参照したことと、本アプリで補正効果を検証したことは区別して記録する。

## 利用者から見た動作

### 設定項目

現在の「色補正」は`none`と`oklch`の択一である。
[設定定義](../../../shared/src/settings/terminal-settings.cpp)と[設定画面](../../../shared/src/settings-widget/settings-widget.cpp)を拡張し、再配色とOklch補正を独立して選べるようにする。

| 項目 | 選択・操作 | 目的 |
| --- | --- | --- |
| 色の区別を補助 | なし、P型向け、D型向け、T型向け | 色覚特性に合わせた再配色を選ぶ |
| 補正の強さ | 表示を見ながら調整する | 利用者が区別しやすい補正量を選ぶ |
| 明暗差を改善（Oklch） | ON／OFF | 再配色と独立して文字やマーカーの明暗差を整える |
| プレビュー | 補正前後を比較する | 型名を知らなくても、見分けやすい設定を選べるようにする |

再配色は初期状態で無効とする。
補正の強さは見やすさを調整する値として表示し、色覚特性の程度を測定する値にはしない。
設定値の名前と保存形式は、独立した選択ができるよう段階2で定める。
補正量のゼロでは再配色による変化をなくし、OklchのON／OFFは別に反映する。

既存の設定継承とApply、Save、Cancelに対応する。
グローバル設定と接続別設定の双方で選択でき、保存後の再起動でも同じ表示を得られるようにする。
再配色だけ、Oklchだけ、両方有効、両方無効の組み合わせを検証する。

### 比較プレビュー

プレビューには、色見本、差分表示、ログ、色付き背景を持つ文字を含める。
色見本だけでなく、文字を読み分ける作業として比較できる構成とする。
ANSI16色、256色、TrueColorと、明るい背景・暗い背景を確認できるようにする。
見本には文字による識別子も付け、設定を選ぶ操作自体が色だけに依存しないようにする。

プレビューと実端末では、同じ補正処理を使う。
再配色の種類、強さ、Oklchの設定を変えた結果を、その場で比較できることを目指す。
実際の通信内容やログへプレビュー用のデータを混ぜない。

### 補正する色と適用範囲

文字色、アプリが指定したセル背景色、下線、カーソル、検索・選択などのマーカーを対象とする。
背景色も対象に含めることで、色付き背景で状態を示す端末アプリに対応する。
接続の識別に使う既定背景は保ち、色の由来に基づいて扱いを分ける案とする。
反転表示では前景・背景の位置が入れ替わるため、表示上の位置だけで既定色を判定しない。

Oklch単独では、現在と同じく背景色を補正しない。
再配色と併用するときは、再配色後の背景を基準に文字やマーカーの明暗差を調整する。
補正対象は描画色であり、送受信内容、端末内の論理色、コピー、ログは変更しない。

背景画像、透過先のデスクトップ、Kitty画像、カラー絵文字の画素は、この色フックでは補正できない。
背景の不透明度も変更対象に含まれない。
この制限は[boxrigの色補正文書][boxrig-color-filters]と[公開APIのコメント][boxrig-color-api]に基づく。
コントラスト評価の基準はセルの背景色とし、画像や透過先を合成した最終画素についての保証とは区別する。

## 現在のコードへの組み込み方針

[TerminalColorFilterContext](../../../elder-terms-terminal/src/terminal-color-filter.h)は、現在は接続の背景色とOklchの有効状態を保持している。
再配色の種類と強さを加え、[既存の描画色フック](../../../elder-terms-terminal/src/terminal-color-filter.cpp)で処理する。
設定から描画へ反映する箇所は[terminal-presentation.cpp](../../../elder-terms-terminal/src/terminal-presentation.cpp)である。
既存の公開APIで実装できる見込みであり、外部依存コードやサブモジュール内のソースは変更しない。

処理順は「接続の既定色を解決 → 色覚向け再配色 → Oklchで明暗差を調整」とする案で評価する。
最後の明度調整で色同士の差が縮む可能性があるため、受入判定には両方を適用した最終色を使う。
再配色だけの結果が良好でも、併用後に識別できなくなる場合は方式を見直す。

boxrigは反転済みの色と、マーカーの下にある補正済みのセル色を渡す。
反転を二重に適用せず、下地の色は参照用として扱う。
前景色に追従する下線は、その継承関係を保つ。
同じ入力と設定からは同じ結果を返し、呼び出し順や時刻によって色を変えない。
設定の変更時には、[表示先APIの契約][boxrig-view-api]に従って色を再計算させる。
これらの契約は実装時にも公式文書とAPIコメントの両方で確認する。

## 検証方針

識別の評価では、代表的な色の組み合わせについて補正前後の模擬表示を比較する。
評価に用いる色、模擬モデル、指標、合格条件は段階1で定める。
特定の補正結果をそのまま期待値にするだけでなく、色の区別が改善することを確認する。
Oklch上の色差だけで、色覚特性に応じた識別を保証したとは扱わない。
また、任意の全色対で同時に識別が改善することは受入条件にしない。
代表色の改善と、別の色の区別が失われるケースを併せて記録する。

| 検証対象 | 確認すること |
| --- | --- |
| 再配色 | P型・D型・T型それぞれの代表色の識別と、強さを変えた結果 |
| 色の安定性 | 補正なし・補正量ゼロ、無彩色、色範囲の境界、同じ入力への再現性 |
| Oklchとの併用 | 最終色での識別と、背景に対する4.5:1以上のコントラスト |
| 色の指定方法 | ANSI16色、256色、TrueColor、アプリによるパレット変更 |
| 描画対象 | 文字、明示背景、既定背景、下線、反転、カーソル、IME、検索・選択マーカー |
| 設定 | 継承、Apply、Save、Cancel、再起動、補正設定の組み合わせ |
| 描画方式 | OpenGLとCairoの実画面で補正が反映されること |
| データの保持 | 送受信内容、論理色、コピー、ログへ影響しないこと |
| 利用者の評価 | 当事者が差分やログを読み分けやすくなること |

既存の[C++色補正試験](../../../elder-terms-terminal/tests/cpp/terminal-color-filter-test.cpp)と[GUI試験](../../../elder-terms-terminal/tests/terminal-color-filter.test.ts)を拡張する。
コードの変更前に、追加する振る舞いを確認するテストのREDを確認する。
実装後にGREENを確認し、段階ごとにコミットする。
画像比較のマスターを追加・変更する場合は目視確認する。
待機は状態変化で判定し、時間軸の問題が見つかった場合には動画による検証を追加する。

模擬表示による評価と、当事者による読み取り評価は別々に記録する。
当事者による評価が未実施の場合は、その受入条件を未完了のまま残す。
4.5:1の基準は既存Oklch補正と[文字のコントラスト指標][wcag-contrast]に合わせる。
この数値だけで、色同士の区別や機能全体のアクセシビリティを保証するものとは扱わない。

## 実施記録

### 段階1の方式選定と検証

模擬モデルにはBrettel方式のsRGB向け係数を採用した。
係数と参照実装は[libDaltonLensの固定リビジョン][daltonlens]に基づく。
公開された係数はパブリックドメインであり、外部コード自体は変更していない。
参照実装を別途実行し、RGB原色と`#7850d2`の模擬結果を照合した。
整数化の丸め方の違いを除き、各成分の差は1以下だった。

[Machadoらの方式][machado]も調査したが、原論文はT型を対象外としている。
今回は三つの型に同じ根拠を使えるBrettel方式を選んだ。
これは模擬表示の選定理由であり、補正効果の実証とは分けて扱う。

再配色では、線形RGBと模擬結果との差から、型ごとに失われる成分を求める。
P型・D型では青と緑の差へ、T型では赤と緑の差へ情報を移す。
緑の調整量にはsRGBの輝度係数を使い、色範囲へ丸める前の輝度変化を抑える。
補正方式と転送量は本アプリで選んだ値であり、臨床上の特性や程度を表さない。
模擬結果を先に色範囲へ丸めると失われた成分を取得できないため、丸めは再配色の最後に行う。

一般的な赤の誤差を緑・青へ同方向に加える候補では、Oklch併用後に赤・緑の差が縮んだ。
色相を保つ彩度低減や中性色への圧縮も比較したが、T型の代表色などで差が縮む場合があった。
そのため、上記の別の色差へ移す方式と、最終段階でのRGB範囲への丸めを採用した。
最大転送量を1にするとP型で明るい赤とマゼンタ、緑とシアンが同じRGBになる問題を再現した。
これを防ぐテストを追加し、最大転送量を0.75にした。
設定では0〜100の整数を使い、100をこの上限に対応させる。
強さの既定値は100、種類の既定値は無効とする。

評価指標は、模擬した二色のOklab座標間の距離とした。
合格条件は補正前から0.02以上の増加、補正後の距離0.04以上である。
これは回帰を検出するための基準であり、人の識別限界を示す値ではない。
P型・D型ではANSIの暗い赤・緑と明るい赤・緑、T型では暗い緑・シアンと明るい緑・シアンを評価した。
背景は黒、`#202020`、白とし、Oklchの有効・無効を組み合わせた。
最大強度で得られた各条件の最小値は次のとおりである。

| 型 | 距離の増加量の最小値 | 補正後の距離の最小値 |
| --- | --- | --- |
| P型 | 0.06388 | 0.25829 |
| D型 | 0.02053 | 0.10632 |
| T型 | 0.06253 | 0.09080 |

ANSI16色の全120組についても増減を調べた。
背景`#202020`、Oklch有効では、0.005を超えて改善した組数はP型48、D型25、T型28だった。
同じ幅を超えて差が縮んだ組数は、それぞれ21、70、66だった。
最大の減少量はP型の明るい赤・マゼンタで0.27228、D型の暗い黄・明るいマゼンタで0.19118、T型の暗いシアン・明るいマゼンタで0.21860だった。
代表色の改善は確認できたが、配色全体に一律の改善はない。
再配色単独でANSI16色の異なる入力が同一RGBにならないことも試験した。
Oklchによる無彩色の統合や、任意のTrueColorの組み合わせまで区別を保証する条件ではない。

`terminal-color-vision-demo`は補正前後、模擬結果、明示背景を並べる実行可能なドライバーである。
次のコマンドで比較と数値結果を再現できる。
表示に使う端末自身の色フィルタは無効にする。

```sh
meson compile -C .build terminal-color-vision-demo terminal-color-vision-test terminal-color-filter-test
.build/elder-terms-terminal/terminal-color-vision-demo deutan 100 '#202020' on
.build/elder-terms-terminal/terminal-color-vision-demo --report
meson test -C .build --no-rebuild terminal-color-vision-test terminal-color-filter-test --print-errorlogs
```

模擬処理、補正処理、ANSI色の重複防止について、未実装・未修正時の失敗を確認してから実装した。
上記のC++試験は両方成功した。
全256段階の無彩色、補正量ゼロ、異常な強度入力、RGB格子4096色の強度変化と再現性も確認した。
実端末では三つの型と明暗二つの背景の計6画面を撮影し、文字、色見本、明示背景を目視した。
数値と画像は`artifacts/plan5/stage1/`に出力した。
目視は表示の確認であり、当事者による読み取り評価は未実施である。

### 段階2の設定と実端末への適用

`terminal.color_vision`に`none`、`protan`、`deutan`、`tritan`を追加した。
`terminal.color_vision_strength`は0〜100の整数である。
既存の`terminal.color_filter=none|oklch`と独立して保存・継承する。
設定画面では不正な強度を入力するとApplyとSaveを無効にし、空欄で継承へ戻す。

描画フックでは、既定色の解決、再配色、Oklchの順で適用する。
再配色は色の由来を参照し、既定背景は反転表示でも保持する。
反転で文字側へ移った既定背景に対するOklchの明暗差調整は、既存の動作を維持する。
明示背景は再配色し、その補正後の背景で文字と下線の明暗差を評価する。
マーカーの下地は補正済みの色として参照するだけで、再配色を繰り返さない。

設定と描画フックの試験を先に追加し、既定値が見つからない失敗と、明示背景が補正されない失敗を確認した。
設定画面の試験では、新しい項目が見つからない失敗を確認した。
実装後は設定、既存Oklch、再配色のC++試験が成功した。
実際にboxrigへANSI色、256色、TrueColor、下線、反転を入力し、四つの補正設定と色・コピーの保持も確認した。
カーソル、検索・選択、hover、IMEについては、各対象のフック入力で色と下地の保持を検証した。

設定画面では、種類と強度の保存、範囲外の拒否、ゼロの許容、継承への復帰、項目の配置を確認した。
実端末のGUI試験12件はOpenGLとCairoで成功した。
既存Oklchの明暗三背景に加え、P型・D型・T型ごとの継承、Apply、Cancel、強度ゼロ、Save、再起動を含む。
ANSI色、256色、TrueColorの文字と明示背景を画面の画素で照合し、受信ログが元のバイト列のままであることも確認した。
記録は`artifacts/plan5/stage2/`と`test-results/20261020_120609_596/`にある。
全体回帰と比較プレビューの確認は、次の段階で行う。

## 色以外の手がかりと今回の範囲

端末アプリが出力する色の意味までは、フィルタから判断できない。
elder-terms自身が表示する状態では、文字や形も併用する方針とする。
これは[W3Cの色の使用に関する指針][wcag-color]を参考にする。
本計画では、色から意味を推測して本文や記号を追加する機能は扱わない。

今回の保存作業の完了条件は、検討した方式の比較、設定、適用範囲、制約、評価、段階別の完了条件をplan5として残すことである。
保存だけの作業では、実装段階の完了条件を満たしたとは扱わない。
計画書はビルド入力に含まれないため、この文書だけの追加ではビルド・全体テストを行わない。
